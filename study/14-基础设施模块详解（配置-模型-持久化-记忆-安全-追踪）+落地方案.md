# 14｜基础设施模块详解（配置 / 模型 / 持久化 / 记忆 / 安全 / 追踪）+ 落地方案

> 本章聚焦“非业务但决定系统上限”的底座模块。

---

## 1. 配置系统（Config）

### 1.1 模块边界

- 目录：`backend/packages/harness/deerflow/config/`
- 关键文件：`app_config.py`（由 `__init__.py` 暴露）、`model_config.py`、`subagents_config.py`、`skills_config.py`

### 1.2 核心价值

- 把运行时行为参数化，而非硬编码；
- 支持环境差异（本地/测试/生产）；
- 为中间件、工具、模型等模块提供统一配置来源。

### 1.3 落地建议

采用“分域配置 + 聚合配置”模式，不要只用一个巨大配置对象。

---

## 2. 模型工厂（Models）

### 2.1 模块边界

- 目录：`backend/packages/harness/deerflow/models/`
- 关键文件：`factory.py`、`credential_loader.py`、各 provider 文件

### 2.2 核心机制

- 通过模型名解析 provider；
- 封装 thinking/vision 等能力差异；
- 统一凭据读取与模型实例化。

### 2.3 落地建议

优先定义统一 provider 接口，再扩展厂商适配；避免业务层直接写厂商 SDK 调用。

---

## 3. 持久化系统（Persistence）

### 3.1 模块边界

- 目录：`backend/packages/harness/deerflow/persistence/`
- 子域：run_event、feedback、scheduled_tasks、channel_connections、user

### 3.2 核心机制

- 结构化模型 + SQL 操作封装；
- migration 管理（alembic）；
- run/线程相关状态持久化。

### 3.3 落地建议

运行事件（event）与最终状态（checkpoint）分开存；便于调试与审计。

---

## 4. 记忆系统（Memory）

### 4.1 模块边界

- 目录：`backend/packages/harness/deerflow/agents/memory/`
- 关键文件：`manager.py`、`tools.py`

### 4.2 核心机制

- 对话抽取与异步更新；
- 记忆读取/写入工具化；
- 与中间件链集成。

### 4.3 落地建议

先做“总结型短记忆”，再做结构化长期记忆；优先保证记忆误召回可控。

---

## 5. 安全治理（Guardrails + AuthZ）

### 5.1 模块边界

- `backend/packages/harness/deerflow/guardrails/`
- `backend/packages/harness/deerflow/authz/`
- Gateway 鉴权：`backend/app/gateway/auth/`

### 5.2 核心机制

- 请求身份认证（Gateway）
- 工具调用授权（AuthZ）
- 风险行为拦截（Guardrails middleware）

### 5.3 落地建议

分三层做安全：

1. 入口认证；
2. 运行时策略；
3. 工具调用细粒度授权。

---

## 6. 追踪与可观测（Tracing）

### 6.1 模块边界

- 目录：`backend/packages/harness/deerflow/tracing/`
- 关键文件：`factory.py`、`metadata.py`

### 6.2 核心机制

- run 级 trace 元数据注入；
- provider 适配（LangSmith/Langfuse 等）；
- 统一追踪入口工厂。

### 6.3 落地建议

要求每次 run 都有 trace_id，且能关联到 thread_id/run_id/user_id。

---

## 7. 上传与工作区变更（Uploads + Workspace Changes）

### 7.1 模块边界

- 上传：`backend/packages/harness/deerflow/uploads/manager.py`
- 变更：`backend/packages/harness/deerflow/workspace_changes/`

### 7.2 核心机制

- 附件入库与虚拟路径管理；
- 运行期间文件变更扫描与记录；
- 前端可查询 run 级变更摘要。

### 7.3 落地建议

把“生成结果”与“过程变更”分开展示，提升可解释性和可回溯性。

---

## 8. 基础设施层整体落地路线

1. 先打配置系统；
2. 再接模型工厂；
3. 再接持久化（run + event）；
4. 再接安全治理；
5. 再接追踪与记忆；
6. 最后接上传与变更可视化。

---

## 9. 验收清单

- 配置项可覆盖核心运行行为且支持环境差异；
- 模型切换不影响业务逻辑层代码；
- run 状态与事件可完整回放；
- 安全策略默认收敛且可审计；
- trace 能串起一次 run 的完整链路；
- 附件和工作区变更可在前端可视化。
