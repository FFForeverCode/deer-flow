# DeerFlow 是 Agent 系统吗？"运行时"又是什么意思？

> 本文用项目内的真实代码证据，回答两个核心概念问题。适合初次接触 Agent / Harness 概念的工程师阅读。

---

## 一、DeerFlow 是 Agent 系统吗？

**是，而且是一个"完整的 Agent 系统"，不只是一个会调用工具的聊天机器人。**

### 1.1 代码证据：它真的构建了一个 Agent

在 `backend/packages/harness/deerflow/agents/factory.py` 中，可以看到它直接基于 LangChain 的 Agent 原语构建：

```python
from langchain.agents import create_agent           # ← LangChain 的 Agent 构建原语

def create_deerflow_agent(model, tools, ...):
    return create_agent(
        model=model,          # 大模型（大脑）
        tools=effective_tools, # 工具（手脚）
        middleware=...,        # 中间件（神经系统）
        checkpointer=...,      # 持久化（记忆）
        ...
    )
```

一个系统能被称为 "Agent 系统"，通常需要满足以下要素，DeerFlow 全部具备：

| Agent 要素 | 含义 | DeerFlow 中的体现 |
|-----------|------|------------------|
| **大脑（LLM）** | 用大模型做决策 | 动态模型选择，支持 thinking/vision |
| **感知** | 能接收环境输入 | 上传文件、图像、对话上下文注入 |
| **行动（Tools）** | 能调用工具改变世界 | `bash`、`read_file`、网搜、MCP 工具等 |
| **自主循环** | 自己决定"下一步做什么" | LangGraph 状态图驱动的 think→act→observe 循环 |
| **记忆** | 跨轮次/跨会话保留信息 | checkpointer 持久化 + 长期记忆系统 |
| **规划分解** | 拆解复杂任务 | TodoMiddleware（规划模式）+ 子智能体派生 |
| **多智能体** | 能派生协作者 | `task()` 工具派生子智能体并行执行 |

### 1.2 它不是"普通聊天机器人"的关键区别

普通聊天机器人：**你问 → 它答**，一问一答，无法真正"做事"。

DeerFlow 这样的 Agent 系统：**你给目标 → 它自己规划 → 调用工具 → 观察结果 → 再决策 → 循环直到完成**。

它有一台"真正的电脑"（沙箱 + 文件系统），能：
- 执行 shell 命令
- 读写、编辑文件
- 上网搜索和抓取
- 派生多个子智能体并行干活
- 把结果收敛成报告、网页、幻灯片等交付物

这就是"Agent（智能体）"和"Chatbot（聊天机器人）"的本质差别。

### 1.3 更进一步：它是"多智能体"系统

DeerFlow 不止一个 Agent：

- **Lead Agent（主智能体）**：运行入口，负责总体规划与调度。
- **Sub-Agents（子智能体）**：主智能体通过 `task()` 工具按需派生，每个有独立上下文、工具集和终止条件，可并行执行（每轮最多 3 个），再把结构化结果汇报给主智能体收敛。

所以准确说法是：**DeerFlow 是一个多智能体（Multi-Agent）编排系统。**

## 二、"运行时（Runtime / Harness）"是什么意思？

这是理解 DeerFlow 定位的关键词。README 把它定义为 **"Super Agent Harness（超级智能体运行时/框架托架）"**，并特意强调：

> "It's no longer a framework you wire together. It's a super agent harness — batteries included."
> （它不再是一个需要你自己接线组装的框架，而是一个自带电池、开箱即用的智能体运行时。）

### 2.1 "运行时"的通俗解释

**"运行时"= 让程序（这里是 Agent）能真正跑起来所需的一整套环境和基础设施。**

打个比方：

| 类比 | 说明 |
|------|------|
| **JVM 之于 Java 程序** | Java 代码本身不能运行，需要 JVM 这个"运行时"提供内存管理、垃圾回收、线程调度。同理，一个 LLM 本身只会"输出文字"，需要 DeerFlow 这个"运行时"提供工具、沙箱、记忆、调度，才能真正"干活"。 |
| **操作系统之于应用** | 应用不用自己管理硬件，操作系统统一提供文件系统、进程、网络。DeerFlow 也统一给 Agent 提供文件系统、执行环境、记忆等。 |
| **汽车底盘（Chassis）之于整车** | Harness 直译是"马具/托架/线束"，即把发动机（LLM）装上去就能开的完整底盘。 |

### 2.2 DeerFlow 作为"运行时"提供了什么？

一个裸的大模型只能生成文本。DeerFlow 这个运行时在它周围包裹了一整套基础设施，让它变成能干活的 Agent：

```
        ┌─────────────────────────────────────────┐
        │         DeerFlow 运行时 (Harness)         │
        │                                           │
        │   ┌───────────┐                           │
        │   │  LLM 大模型 │ ← 你插入的"发动机"          │
        │   └───────────┘                           │
        │        ▲                                  │
        │        │ 运行时为它提供：                    │
        │  ┌─────┴─────────────────────────────┐   │
        │  │ • 文件系统 (workspace/uploads/...)   │   │
        │  │ • 沙箱执行环境 (bash / 代码执行)       │   │
        │  │ • 工具系统 (网搜/抓取/MCP/自定义)       │   │
        │  │ • 长期记忆 (跨会话)                    │   │
        │  │ • 技能加载 (Skills)                   │   │
        │  │ • 子智能体派生与调度                    │   │
        │  │ • 中间件链 (上下文/安全/预算管理)        │   │
        │  │ • 持久化 (checkpointer)               │   │
        │  │ • 流式回传 / 可观测性追踪               │   │
        │  └────────────────────────────────────┘   │
        └─────────────────────────────────────────┘
```

**核心含义：你不用自己去实现"怎么让 Agent 记住东西""怎么让它安全执行命令""怎么派生子任务"——这些运行时都帮你做好了。你只需要插入模型、（可选）加上技能，就能用。**

### 2.3 "Framework（框架）" vs "Harness（运行时）"的区别

README 特别强调 DeerFlow 2.0 从 framework 变成了 harness，这个区别很重要：

| | Framework（框架） | Harness / Runtime（运行时） |
|---|------------------|---------------------------|
| **心智模型** | 给你一堆零件，你自己拼装 | 整机交付，插上模型就能跑 |
| **上手成本** | 高，需要理解如何"接线" | 低，开箱即用（batteries included） |
| **DeerFlow 1.x** | 是一个 Deep Research 框架 | — |
| **DeerFlow 2.0** | — | 是一个 Super Agent 运行时 |
| **扩展方式** | 改代码 | 加技能（Skills）、加工具（MCP）、换模型 |

一句话：**运行时 = "开箱即用 + 完全可扩展"的 Agent 执行底座。**

## 三、把两者串起来理解

现在可以完整回答了：

> **DeerFlow 是一个"多智能体系统"，同时它本身是一个"运行时（Harness）"——即：它不仅是一个会自主决策、调用工具、派生子智能体的 Agent 系统，更是一套让任何 LLM 都能变成这样的 Agent 的完整基础设施底座。**

用一个流程说明"运行时如何让 Agent 跑起来"：

```
1. 你在 config.yaml 里配好一个模型（插入"发动机"）
        ↓
2. 你发一个任务，比如"帮我调研 X 并生成报告"
        ↓
3. 运行时创建 Lead Agent，注入：系统提示 + 技能 + 记忆 + 工具 + 沙箱
        ↓
4. Agent 开始自主循环：思考 → 调用工具(搜索/写文件/派生子智能体) → 观察 → 再思考
        ↓
5. 运行时全程托管：管理上下文预算、拦截危险操作、持久化进度、流式回传
        ↓
6. 任务完成，产出交付物（报告/网页/幻灯片），并异步抽取记忆供下次使用
```

在这个过程中，**你只提供了"目标"和"模型"，其余一切（记忆、执行、安全、调度、持久化）都由 DeerFlow 这个运行时负责——这就是"Super Agent Harness"的完整含义。**

## 四、关键术语速查表

| 术语 | 一句话解释 |
|------|-----------|
| **Agent（智能体）** | 能自主决策、调用工具、循环行动直到完成目标的程序 |
| **Multi-Agent（多智能体）** | 一个主智能体能派生多个子智能体协作 |
| **Runtime（运行时）** | 让 Agent 真正跑起来所需的全套环境与基础设施 |
| **Harness（托架）** | Runtime 的形象说法：插上模型就能用的完整底盘 |
| **Framework（框架）** | 需要你自己拼装的零件集合（DeerFlow 2.0 已超越此形态） |
| **LangGraph** | 底层的 Agent 状态图/循环编排引擎 |
| **Middleware（中间件）** | 在 Agent 每步前后处理上下文、安全、预算等横切关注点 |
| **Sandbox（沙箱）** | Agent 安全执行命令、读写文件的隔离环境 |
| **Skill（技能）** | Markdown 定义的可插拔能力模块，按需加载 |
