# 15｜前端与多渠道接入模块详解 + 落地方案

> 覆盖模块：Frontend 线程流、API 客户端、任务展示、Gateway Channels（Slack/Telegram/Feishu/...）。

---

## 1. Frontend 线程流模块

### 1.1 模块边界

- 线程核心：`frontend/src/core/threads/hooks.ts`
- API 客户端：`frontend/src/core/api/api-client.ts`
- 任务视图：`frontend/src/core/tasks/`

### 1.2 关键机制

1. `sendMessage(...)` 统一提交入口；
2. optimistic UI + 附件预上传；
3. `thread.submit(..., streamSubgraphs/streamResumable)` 发起流式 run；
4. 对 run cancel / reconnect 做兼容处理。

### 1.3 为什么这样设计

- 降低交互延迟感；
- 保障附件路径先可用再交给模型；
- 流式异常（断线/终态 race）有可恢复策略。

---

## 2. 前端子任务与步骤展示

### 2.1 模块边界

- 目录：`frontend/src/core/tasks/`
- 关联组件：`frontend/src/components/workspace/messages/`

### 2.2 关键机制

- 从 `task_running` / `subagent.step` 等事件累计步骤；
- 终态回写后做折叠与摘要展示；
- reload 后可基于 events endpoint 回补步骤历史。

### 2.3 落地建议

事件模型要采用“增量追加 + 去重”策略，避免晚到帧覆盖已有状态。

---

## 3. Gateway 多渠道接入（IM Channels）

### 3.1 模块边界

- 目录：`backend/app/channels/`
- 关键文件：`manager.py`、`run_policy.py`、`slack.py`、`telegram.py`、`feishu.py`、`discord.py`

### 3.2 核心机制

1. 各渠道做消息协议适配；
2. 统一回收为 run 请求参数；
3. 通过 Gateway run path 执行，而不是另起执行栈；
4. 根据渠道能力选择 wait/stream 回传。

### 3.3 为什么这样设计

- 同一 Agent Runtime 复用，避免多套行为不一致；
- 渠道差异只停留在输入/输出适配层；
- 便于统一权限、审计、计费与观测。

---

## 4. 端到端链路（Web 与 IM 对比）

### 4.1 Web 链路

`threads/hooks.ts -> api-client.ts -> thread_runs.py -> services.py -> run_agent -> SSE -> 前端渲染`

### 4.2 IM 链路

`channels/*.py -> channels/manager.py -> Gateway run path -> run_agent -> 渠道适配回包`

共同点：都走同一 run 生命周期。

---

## 5. 完整落地方案

### 5.1 前端层

1. 建立统一发送钩子（含 optimistic + upload + submit）；
2. 建立统一 stream 状态机（loading/cancel/reconnect/end）；
3. 建立任务卡片数据模型（步骤、终态、usage）。

### 5.2 多渠道层

1. 定义统一 `InboundMessage` 协议；
2. 渠道适配器将外部消息转协议对象；
3. Manager 调用统一 run path；
4. 渠道适配器将运行结果转各平台消息格式。

### 5.3 融合层

1. run_id/thread_id 在 Web 与 IM 统一；
2. 统一错误码与重试策略；
3. 统一操作审计与 trace 关联。

---

## 6. 常见坑位

1. **Web 与 IM 分别实现执行逻辑**：最终行为会漂移；
2. **前端只看最终消息，不处理中间事件**：子任务与工具进度不可见；
3. **IM 渠道不做 backpressure 控制**：高峰时容易消息风暴。

---

## 7. 验收清单

- Web 与 IM 触发同类任务时，输出行为一致；
- 前端断网重连后不会卡在 loading；
- 子任务步骤在实时与历史回放中一致；
- 渠道连接异常不会影响核心 runtime 可用性。
